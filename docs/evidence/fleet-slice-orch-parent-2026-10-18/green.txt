## 2. What was fixed and why (design decision)

Two failure modes collide for the pass-protocol fleet form when a slice is
path-citing:

1. **B-5 scrub gate** (`tasks.content_ok_for_fleet`, enforced in RLS WITH
   CHECK) correctly refuses paths/email/IP in fleet rows — fleet rows are
   RLS-visible to every profile, so the gate is a deliberate fail-closed PII
   invariant, explicitly tested (`test-tasks-schema.sh` `fleet content abs
   path rejected (scrub gate)`; `test_task_db_unit.py` degrades-to-personal).
   A path-citing STORY therefore degrades to `scope=personal`. This is
   CORRECT and must never be weakened.
2. **check_tenant** then refused a PII-clean fleet SLICE under that
   now-personal story: `slice scope (fleet) exceeds parent scope (personal)`.

The slice's literal acceptance ("assert both store scope=fleet" for a
path-citing story) is only satisfiable by weakening the PII gate (Option A) —
rejected on fail-closed grounds. **Chosen fix (Option B, narrowed):** relax
`tasks.check_tenant` so a fleet slice may sit under a PERSONAL story owned by
an orchestrator (`created_by IN ('moses','esther')` — the same hardcoded
allowlist `verify_slice` uses, v009). The slice's OWN content is still held
PII-clean by RLS WITH CHECK + the fleet-writer role, so no PII can leak into a
fleet row; non-orchestrator personal parents stay refused (coherence).
