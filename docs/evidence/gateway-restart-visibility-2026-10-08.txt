restart visibility — "/restart gave no indication it happened" (reported 2026-10-08)
====================================================================================

WHAT WAS REPORTED. After pressing /restart in the pi-backed bot: no indication that it
had actually restarted, and the conversation continued unchanged.

WHAT WAS TRUE. The restart HAD happened — systemd restarted the unit (NRestarts=1, new
MainPID, 5s gap). Nothing was broken in the mechanism. Two things conspired to hide it:

  1. The only message about the restart was sent BEFORE the drop, by the process that
     then exited. Nothing was said afterwards, so from inside the chat the restart was
     invisible.
  2. The conversation is deliberately preserved across a gateway restart (that is what
     /new is for). Asked afterwards "did you restart?", the AGENT answered "No, I
     didn't restart. I still have our conversation context…" — true of the session,
     false about the gateway, and the only answer available to the human.

THE FIX (three parts, each addressable separately):

  * `/restart`'s reply now states what happens to the CONVERSATION ("This conversation
    continues (send /new for a fresh session); I'll confirm as soon as I'm back."),
    because "restart" reads like "fresh start" and this is not one.
  * The NEW process announces itself at startup, BEFORE polling, with the operator's
    wording: "♻ Gateway restarted successfully. Your session continues." A chat should
    not have to speak first to learn the gateway is back.
  * The AGENT is told the same fact on its first prompt after the restart, so it can
    answer truthfully. The marker outlives the announcement (the human was told at
    startup; the agent still needs the fact) and is consumed by that turn. If the
    startup announcement could not be delivered, the marker survives and the first
    reply carries the confirmation instead — the news is never lost to a failed send.

LIVE PROOF (real systemd, deployed code, a scratch user unit; the live bot's chats and
state untouched — scratch chat id, scratch books, no polling). Start 1 runs the REAL
/restart handler; start 2 is the new process mirroring main()'s startup path:

READING THE CAPTURE: start 1 replies and exits (systemd logs "restart counter is at 1");
start 2 — a new process — finds the marker, sends the confirmation WITHOUT the human
saying anything, then serves one real pi turn in which its prompt carries "[system] The
GATEWAY PROCESS restarted" (read out of the session transcript, since pi does not echo
the prompt), and the marker is consumed.

HONEST NOTE ON THE PROBE: the capture continues past this point with further restarts
that report "FAIL announcement: told=0". Those are the PROBE's own artifacts, not the
product's: its unit is Restart=always and it exits non-zero on the assertion, so it
restarted itself in a loop, and on every pass after the first the marker had already
been legitimately consumed — so there was correctly nothing to announce. The first pass
is the authoritative one. (The probe has no self-stop, which is why it looped; the unit
was stopped and removed immediately.)
