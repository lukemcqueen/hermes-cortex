FINDING (found by this evidence, fixed here): /compact hung ~40% of the time
---------------------------------------------------------------------------
Symptom: `pi-control: pi did not answer within 300s`, intermittently, and only when
the gateway ran the control command (the same command from a shell always answered
in ~2s). Diagnosis, in order:

  1. Not the session: a not-yet-existing transcript made pi's RPC `compact` never
     answer at all (45s+, repeated), while `get_state` on the same id answered in
     1.2s and created it. Fixed in the adapter: `compact` now does a `get_state`
     round trip first and answers "this chat has no conversation yet" instead of
     asking blind. Held by test_pi_control_does_not_hang_on_a_chat_that_has_no_session_yet.
  2. Still ~40% hangs with the real session. Instrumented (CORTEX_PI_CONTROL_DEBUG=1):
     the pi process was ALIVE and silent for the whole deadline, writing nothing to
     stdout or stderr — not an EOF/pipe artifact.
  3. `--no-mcp` fixes it. pi connects its four MCP servers at RPC startup; a CONTROL
     call (state/compact) uses no MCP tool, so the servers are pure risk. Measured
     on the trigger sequence (print-mode turn + check_model + compact):

         with MCP:     4 fast, 2 hangs at 25-60s   (earlier runs: 12.5% - 50%)
         with --no-mcp: 8/8 answered, 1.1-1.2s each

     Held by test_pi_control_runs_its_rpc_calls_without_mcp (asserts the argv).
  Also hardened: pi is started in its own process group, so a timeout reaps pi AND
  its MCP children instead of leaving them holding the adapter's pipes.

/restart under real systemd — proven, not asserted
--------------------------------------------------
The handler refuses when the daemon is NOT the unit's main process (the transcript
in step 6 shows exactly that refusal, because this script is not). The accept path
was proven with a throwaway user unit running the DEPLOYED gateway code with a stub
transport, `Restart=always`, on this host (unit and probe removed afterwards):

    Oct 08 16:04:03 systemd[1099]: Started cortex-gateway-restart-probe.service …
    Oct 08 16:04:03 python[3858592]: START pid=3858592 unit='cortex-gateway-restart-probe.service' supervised=True
    Oct 08 16:04:03 python[3858592]: FIRST_START — invoking the /restart handler now
    Oct 08 16:04:03 python[3858592]: SENT 🔄 restarting the gateway — back in a few seconds…
    Oct 08 16:04:08 systemd[1099]: cortex-gateway-restart-probe.service: Scheduled restart job, restart counter is at 1.
    Oct 08 16:04:08 python[3858740]: START pid=3858740 unit='cortex-gateway-restart-probe.service' supervised=True
    Oct 08 16:04:08 python[3858740]: SECOND_START_OK — systemd restarted the unit after the /restart exit

So: the reply is delivered, the exit happens, and systemd brings the unit back —
NRestarts=1 and a fresh MainPID, both observed.

Note on the supervision check: INVOCATION_ID alone is NOT sufficient — systemd
exports it into the whole process tree, so a daemon started by hand from inside
another service sees it too. The check therefore also requires our own cgroup to
name a unit AND our PID to be that unit's MainPID; anything unverifiable refuses.


Live-path caveat, stated rather than hidden
-------------------------------------------
Every check above runs through the real gateway object with the deployed modules and
a real pi process; the TELEGRAM leg (a human's message arriving from the Bot API) is
the one part a script cannot exercise without becoming a second poller. That leg is
covered separately by docs/design/gateway-reply-path.md (message_id 8 delivered to
the second bot). A human pressing the buttons in @Esther0001Bot is the last mile.
