# hermes update: "Could not resolve the stable source channel ... timed out after 10 seconds"

Provenance: captured 2026-10-19 on the host running the affected Hermes checkout.
Commands were run against the live checkout; outputs below are verbatim (host home
paths normalised to `~`). Nothing here is a proposal — it is what the tools printed.

## Symptom (from ~/.hermes/logs/update.log, lines 6898-6917)

    === hermes update started 2026-10-18T02:42:00 ===
    → Fleet: 1 running service(s) across profiles: default
    → Update channel: stable
    ✗ Could not resolve the stable source channel: Command '['git', 'merge-base',
      '--is-ancestor', 'd923a5eb487a17c0a68801bba9ef0f56c81040a8',
      '427d605d4985c2d49a795493ef6c5d66413057d1']' timed out after 10 seconds.
      No update was applied.

The same three lines repeat for runs at 2026-10-19T10:09:10 and 2026-10-19T16:22:34 —
3/3 identical, same two SHAs.

`427d605d49` is HEAD. `d923a5eb` is the stable release commit (v0.22.2).

## What makes it take 50 seconds: a commit that is not present locally

    $ time timeout 120 env GIT_NO_LAZY_FETCH=1 git merge-base --is-ancestor \
        1111111111111111111111111111111111111111 HEAD
    warning: lazy fetching disabled; some objects may not be available
    fatal: Not a valid commit name 1111111111111111111111111111111111111111

    real    0m50.733s
    user    0m50.447s     # CPU-bound, not network-bound
    sys     0m0.280s
    rc=128

With `GIT_TRACE=1` the trace stops after the lazy-fetch warning; no further trace
events are emitted while it burns the CPU. Removing the promisor did not change it
(`git -c remote.origin.promisor=false ...` → still 51s, rc=128 with the guard;
60s+ timeout without it).

50s > the call's `timeout=10` → `subprocess.TimeoutExpired` → the reported error.

## Why the release commit was not present

    $ git branch -a --contains d923a5eb...
    (empty)
    $ git tag --contains d923a5eb...        # before the fix
    (empty)
    $ git ls-remote origin | grep d923a5eb...
    d923a5eb...   refs/heads/release/0.22.2
    d923a5eb...   refs/tags/abandoned-rc.1-v0.22.2^{}
    d923a5eb...   refs/tags/rc.1-v0.22.2^{}
    d923a5eb...   refs/tags/rc.2-v0.22.2^{}
    d923a5eb...   refs/tags/v0.22.2^{}

The clone fetches only `refs/heads/main`, and local tags were stale — so the
release commit could only arrive by lazy fetch. `git rev-parse --verify
refs/tags/v0.22.2` printed ABSENT before the fix.

The guard that suppresses the lazy fetch landed 2026-09-23:

    $ git log --format='%h %ad %s' --date=short -S GIT_NO_LAZY_FETCH -- hermes_cli/_subprocess_compat.py
    58f3bf10c0 2026-09-23 fix: startup update check no longer lazy-fetches history in partial clones

The update flow fetches the target ref only AFTER channel resolution
(`hermes_cli/update_cmd.py:1899`), so it cannot help the probe that runs first.

## Fix applied

`refs/tags/v*:refs/tags/v*` is the shape hermes itself already uses
(`hermes_cli/gitlock.py:685`); the same refspec was added to this clone's
`remote.origin.fetch` and the tags fetched:

    $ git config --add remote.origin.fetch '+refs/tags/v*:refs/tags/v*'
    $ time git fetch --no-tags origin 'refs/tags/v*:refs/tags/v*'
     * [new tag]  v0.22.2 -> v0.22.2
     * [new tag]  v0.22.2+canary.20261016T065950Z -> ...
     * [new tag]  v0.22.2+canary.20261019T071120Z -> ...
    real 0m4.7s

## Residual / not covered

- `rc != 0` is handled as "not an ancestor" by `source_releases.py:116-122`; only
  the TIMEOUT is fatal. A fast failure would let the update continue.
- The release commit for a future release is again absent until a fetch lands, and
  the probe runs before the update's own fetch. The added refspec means any future
  `git fetch` in this clone pulls new `v*` tags; nothing in the probe path fetches.
- Not tested: any host other than this one, and any git newer than 2.43.0.
