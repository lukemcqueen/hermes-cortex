pi has no memory — "the cortex store is not reachable from this host" (fixed 2026-10-08)
=====================================================================================

WHAT WAS REPORTED. The pi backend of @Esther0001Bot answered "memory unavailable — the
cortex store is not reachable from this host", while Hermes Esther on the SAME host had
memory. Same database, same credentials, same container — one harness had memory, the other
did not.

ROOT CAUSE (diagnosed by the concurrent session bg_185637_492530, whose regression test is
committed as tests/test_no_new_privs_sg_store.py). Both access layers reached Postgres on
Linux ONLY through `sg docker -c "docker exec … psql …"`. `sg` calls setgroups()/setgid()
unconditionally, and the kernel refuses that under `NoNewPrivileges=true` — which the
serving unit (cortex-gateway-esther0001.service) sets. The process already HELD the docker
group; the group switch was pure ceremony, and it was what broke. `available()` then
swallowed the exception and returned a bare "unavailable", so a hardening flag was reported
as a database outage.

Measured, the two directions (from the committed detector):
  setpriv --no-new-privs -- sg docker -c "docker exec … psql …"   -> rc=1, "setgid: Operation not permitted"
  setpriv --no-new-privs --      docker exec … psql …             -> rc=0, returns 1

THE FIX — the ORDER was the bug. `_attempts()` builds an argv LADDER:
  1. DIRECT `docker exec … psql -w …` — no group switch, survives NoNewPrivileges=true.
  2. `sg docker -c "docker exec … psql -w …"` — the FALLBACK, kept deliberately: it is the
     only path on a host whose user is not in the docker group. Dropping it outright would
     trade one host's outage for another's.
Applied to BOTH access layers, which are required to stay in step:
  ops/services/mycortex-mem/store.py        (the shared surface)
  plugins/mycortex-mem/__init__.py          (the Hermes plugin adapter)
A failure now names EVERY cause ("docker: … | sg: …") instead of one line, and the reason a
`available()` returned False is kept in `last_error`, so "memory unavailable" can be told
apart from "the database is down". `available()` itself stays fail-open (False, never
raises) — that contract is unchanged.
