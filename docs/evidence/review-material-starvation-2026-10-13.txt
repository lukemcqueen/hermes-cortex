2. The defect, isolated
-----------------------
`_bound_per_file()` divides a fixed character budget across every changed file so
that no file is invisible entirely. Its guarantee per file is
REVIEW_MATERIAL_MIN_SLICE = 200 chars — sized for "the file is represented", not
for "the file can be judged".

Cycle 12466 was a 9-file change against the 12000-char budget. The file under
review was mcp-servers/loop-gov-mcp.py — on the ALWAYS_REVIEW surface, i.e. the
one artifact the review exists to judge. It was shown as 3000 of 49429 chars.
6.1%.

The reviewer filed seven unverified-claim findings against exactly that, and they
were all true statements about the material. Measured directly against the old
code (budget=12000, no priority):

  mcp-servers/loop-gov-mcp.py               3000/49429 shown (6.1%)  BOUNDED
  tests/test_lock_liveness_activity.py      1750/15015 shown (12%)   BOUNDED
  tests/test_run_tests_wrapper.py           1750/13365 shown (13%)   BOUNDED
  docs/DOCS-INDEX.md                        1750/8537  shown (20%)   BOUNDED

Note honestly: the after-share is a flat 2x-floor priority (5000) capped by what
one file may take, not proportional growth. The raw PERCENTAGE on an outsized
file is not the metric that matters — ABSOLUTE reviewable chars, and the file
ranking above its auxiliaries, are. The budget raise is what moves the absolute
number; the priority is what stops the always-review path ranking last.


3. Change 1 — always-review priority (_bound_per_file, Pass 0)
--------------------------------------------------------------
New constant REVIEW_MATERIAL_ALWAYS_REVIEW_PRIORITY = 2 x
REVIEW_MATERIAL_PER_FILE_FLOOR (5000).

Pass 0 takes an always-review share FIRST, out of the budget and before the
floor or the equal-share pass can allocate, so it cannot be eroded; then Pass 1
is given the remainder minus what Pass 0 took (floor_budget -= sum(alloc)), so
the floor and the equal share still operate on a consistent pool and no file is
omitted entirely.

It is a REORDERING of an existing budget, not an increase, and it is
anti-gaming: `_is_always_review_path()` uses the same ALWAYS_REVIEW_PATHS
substring predicate as the complexity trigger, so a worker cannot buy a file a
priority share the trigger list would not always-review anyway.

Verified both directions:
  - with an always-review path present: that file ranks first (test below)
  - with no always-review path: priority does not fire, allocation is unchanged


4. Change 2 — DIFF_CHAR_BUDGET 12000 -> 20000
---------------------------------------------
The budget was sized when the reviewer's context was the binding constraint. The
binding constraint now is CONTENT, and the budget manufacturing 35% of the day's
findings costs a full review round each, every time, forever.

REVIEWER_MAX_TOKENS (16000) already bounds the reply, and the raise buys ~8000
more chars of visible change per round at the same per-round shape. It does not
loosen the verdict: the reviewer still sees a bounded window, still fail-closes,
and every bound is still disclosed with true numbers. DIFF_CHAR_BUDGET_DOCS
stays 60000 and remains strictly larger than the standard budget.


5. Change 3 — a wrong-repo guard that refused healthy closes
------------------------------------------------------------
Found by running the gate's own regression suite. Pre-existing, NOT introduced
by this change; reproduced on a clean tree with the change stashed:

  test_gate_skips_simple_change_without_reviewer  FAILED
  assert CallToolResult(... "Cannot close: the lock's repo cannot contain this
  ... commit in that repo.") is None

Root cause: `_candidate_repos()` builds the candidate set by walking HOME, then
UNCONDITIONALLY appends the cwd repo from `git rev-parse --show-toplevel`. When
HOME and cwd are in different universes (a test fixture, a shared checkout,
another user's tree) the guard can name a repo the lock could never have been
about and refuse the close for work that was never there.

Fix: confine the cwd candidate to HOME (`Path(root).resolve().is_relative_to(
Path(HOME).resolve())`); an unresolvable path is skipped, not a crash.

Before:  tests/test_runtime/test_adversarial_review_gate.py  1 failed, 13 passed
After:   tests/test_runtime/test_adversarial_review_gate.py  14 passed


5b. Change 4 — the degenerate-reply crash, claimed fixed and NOT fixed
----------------------------------------------------------------------
A concurrent session on this host committed `fix(review): refuse a degenerate
reviewer response instead of crashing the close`, whose message states the guard
was added to `_extract_verdict` so a None reviewer reply refuses rather than
raising "'NoneType' object has no attribute 'find'". Its own message also records
"NO TEST SHIPPED".

Re-measured against the committed file, that claim is FALSE — `_extract_verdict`
still went straight into `text.find("{")`:

  python3 -c "
  import importlib.util
  spec=importlib.util.spec_from_file_location('lg','.../mcp-servers/loop-gov-mcp.py')
  m=importlib.util.module_from_spec(spec); spec.loader.exec_module(m)
  print(m._extract_verdict(None))"   ->  CRASH: AttributeError
                                          'NoneType' object has no attribute 'find'

This is the recorded "unverified-claim" pattern: a commit message asserting a
result whose producing artifact was never written. Recorded rather than asserted
is better than a false claim, but the crash was still live in production, twice
observed on this host.

Fix (TDD, RED first): four tests added to
tests/test_runtime/test_adversarial_review_gate.py — None, empty/whitespace, and
non-string replies must all return ("FINDINGS", "[]"), plus two controls
asserting the normal parse and the unparseable-prose contract still behave.

  RED:   2 failed, 17 passed  (AttributeError raised from the parse)
  GREEN: 19 passed

Guarded in the SHARED parse rather than at each caller, so both reviewer backends
inherit it — the agent backend already refused silence explicitly; the LLM path
was the weaker one.
