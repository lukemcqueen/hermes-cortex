1. The defect — the ROOT CAUSE of a lock scoped to the wrong repository
   _note_session_repo (governance-enforcer) is documented as recording 'the repo this
   session was last seen USING'. It learned it from the PATH ARGUMENTS of every tool
   call, consulting

       _PATH_ARG_KEYS = ("path", "file_path", "workdir", "cwd", "directory")

   and RETURNING ON THE FIRST KEY PRESENT. So a bare file 'path' outranked an explicit
   'workdir', and ANY call whose path argument landed in another repo re-homed the
   session — including a pure READ. Measured on this host 2026-10-22: a single
   search_files(path=<another repo>), made while surveying that repo, re-homed this
   session. begin_change's _derive_repo_path then resolved source 0 to that repo, the
   lock was recorded against it, the review scope judged ITS blobs, and (before
   eb9a5edf) that lock authorised writes in ANY repo.

   Reading a file is not evidence of WORKING in a repository.

5. What the fix does
   • An EXPLICIT working directory (workdir/cwd) is consulted FIRST. It states where the
     session IS; a bare file 'path' only says what it looked at. 'path' used to be
     consulted first, so the weakest signal always won.
   • A bare file/dir path counts only as evidence of WORK: the call must be write-class
     (_is_write_tool — this module's canonical fail-closed classifier, whose READ_TOOLS
     set already lists read_file and search_files), or the session must not know its repo
     yet, which leaves first-touch learning from any path exactly as it was.
   • The new tool_name argument is optional, so all three existing callers in
     tests/test_loop_gov_review_repo.py keep working unchanged.
