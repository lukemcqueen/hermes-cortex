skill-drift parity verification — how to re-run it
==================================================

Rather than a transcript of somebody's terminal, the verification for the
orch-skill-lifecycle drift reconciliation is two COMMITTED, RUNNABLE scripts.
Run them; do not read assertions about them.

  bash ops/scripts/manage/verify-skill-drift-parity.sh        # the check (C1..C6)
  bash ops/scripts/manage/test-verify-skill-drift-parity.sh   # negative tests

Both exit non-zero when a claim stops holding, so either can gate CI.

What the check proves (C1..C6)
------------------------------
  C1 cortex-doctor ran AND reports no skill drift
  C2 reconcile-stranded-skills.py ran AND reports 0 stranded (repo == deployed)
  C3 repo and deployed copies of both recovered skills are byte-identical
  C4 the two recovered files dropped no repo content (diff ^< empty)
  C5 both files keep an even triple-backtick fence count (FENCE-SAFETY RULE)
  C6 secret-leak-detector ran AND finds nothing blocking

Error policy (SOUL Principle 12 — never swallow errors)
-------------------------------------------------------
A dependency whose run is not EVIDENT is a FAILED check, never a pass. Exit
codes alone are ambiguous for these tools, so each check states its own
run-evidence test:

  C1 cortex-doctor exits 1 whenever ANY warning exists, so rc cannot separate
     "ran fine, warnings present" from "crashed": require >= 100 per-check lines
     (measured 470) or report COULD NOT VERIFY.
  C2 require a line matching `verdict: (PASS|FAIL)`, not the bare substring.
  C3/C4/C5 guard BOTH repo and deployed paths with [ ! -f ] before any diff or
     awk, so a missing file cannot read as "nothing wrong"; C4 also inspects
     diff's exit code (>1 means diff could not run).
  C6 measured clean case is rc=0 with EMPTY output; any non-zero rc or an
     unrecognised rc=0 report is COULD NOT VERIFY.

Negative tests — run `test-verify-skill-drift-parity.sh`
--------------------------------------------------------
That script induces each failure mode in a temp-dir copy of the verifier (never
touching the repo) and asserts a non-zero exit plus the named reason. Last run:
9 probes, 0 blind spots, exit 0. Cases covered: stock verifier passes; a
stubbed-doctor baseline still passes (proving isolation); doctor rc=2 with junk
output; doctor printing no check lines; reconcile printing no verdict; repo copy
missing; deployed copy missing (HOME pointed at an empty dir); scanner non-zero
WITH output; scanner rc=0 with an unrecognised report.

A green run alone proves the checks work; only a demonstrated failure proves
they would catch a regression — which is why the second script exists.
