# The fleet's python dependency set for ~/.steadfaste-fleet/venv — the venv fleet-update.sh
# registers every MCP server against.
#
# Declared because nothing was: the set was only knowable by grepping the repo, so a host
# with a broken venv had no way to know what "fixed" meant. Measured from what the repo
# actually imports (2026-10-13):
#   mcp      -> mcp-servers/*.py, ops/scripts/orch-bus/orch-bus-mcp.py
#   PyYAML   -> fleet-update.sh, install-*.sh, health watchdogs, core/fleet_bus/workflow/
#   fastapi  -> core/fleet_bus/server.py
#   uvicorn  -> core/fleet_bus/server.py (the ASGI server it runs under)
#   psycopg  -> core/fleet_bus/queue.py, ops/scripts/bus/workflow-inspector.py
#   pytest   -> the test suite (dev)
#
# Repair or install on ANY host with one idempotent command that verifies by import:
#   python3 ops/scripts/manage/fix-fleet-venv.py
# Report without changing anything (the shape a doctor check runs):
#   python3 ops/scripts/manage/fix-fleet-venv.py --check
#
# ⚠️ mcp>=2.0, NOT >=1.0 (2026-10-20). The floor is load-bearing: the fleet's MCP
# servers register their handlers through the 2.0 CONSTRUCTOR API
# (Server(name, on_list_tools=..., on_call_tool=...)), which the 1.x SDK rejects with
# "unexpected keyword argument 'on_list_tools'". A floor of >=1.0 admitted exactly the
# version the servers cannot construct against, so a host repaired from this declared
# set could resolve straight back into a broken governance gate (measured on gisu).
# fix-fleet-venv.py also PROBES this capability, not just the import — a version that
# imports but cannot construct the handlers is reported as a gap.
mcp>=2.0

# resolve their TLS CA bundle from certifi.where(). Pin it (and requests) so a silent
# uninstall cannot break TLS — a pip check / pip freeze diff flags a missing cacert.
certifi>=2023.5.7
