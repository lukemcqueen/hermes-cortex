# Cron Failure Restore

Use when a cron job is paused, erroring, or missing runs — and especially when a health-vector / fleet-watchdog alert refires for the same symptom and won't clear. The alert is usually the *symptom*; a dead root-cause handler or an auto-paused cron is the *disease*.

## Always-on rules

- **Auto-restored — but only watchdog-flagged jobs.** `agent-cron-failure-watchdog.py` auto-pauses a cron after 3 consecutive `last_status: error`. `agent-remediate-apply.py` now auto-resumes those every 10 min, but ONLY jobs the watchdog itself flagged (`state: paused` AND alerted with ≥3 strikes in `~/.hermes-cortex/state/cron-failure-watchdog.json`), with a 6h per-job cooldown to bound flapping. Deliberate/operator holds (fleet-wide pause, a superseded duplicate, `NEVER_RESUME` in that script) are never resumed. A genuinely-broken job thus flaps pause→resume→pause, then stays quiet for the cooldown — so auto-resume is bounded, not a live loop. Never assume a paused job comes back in the same tick.
- **A transient failure becomes a permanent silent outage.** One bad tick (Ollama/DB/network blip) that tripped 3 quick failures turns into a cron that never runs again, and the real symptom appears as an unrelated *recurring* downstream alert — a health-vector flag flipping to down (`mycortex`, `no_errored_crons`, a service check) that refires every poll cycle until the underlying cron is resumed. The recurring alert is the tell for an auto-paused cron; investigate it before tuning the alert or chasing the symptom.
- **Before resuming, verify the root cause actually cleared** — the paused job is usually a symptom, not the disease. Run its underlying script (or its dependency) manually and confirm it works first. Resuming a still-broken job is safe (the watchdog re-pauses after 3 more failures) but noisy; confirming first avoids the flap.

## Procedure

### 1. When a recurring alert won't clear, hunt for the auto-paused cron

1. Read `~/.hermes/cron/jobs.json`; find jobs with `paused_at` set / `state: paused` and a `last_run_at` that stopped days ago while sibling jobs kept firing at their cadence.
2. Cross-check `~/.hermes/cron/executions.db` table `cron_incidents` for the "failed 3 consecutive runs — pausing it" marker (per-job `failure_type: script`), and note which job wrote the pause.
3. Trace the alert's dependency chain backward: watchdog flag → `mycortex doctor` / health-vector checks → stale source/state → the paused sync/feed cron. Confirm the alert derives from that cron's inactivity before touching the alert itself.

### 2. Verify and resume

1. Run the paused job's underlying script manually (or hit its dependency) → confirm exit 0 / healthy.
2. Resume via `cronjob` MCP `action=resume` (or `hermes cron resume <job_id>`), then watch the **next scheduled tick** — not a manual run — return `ok`.
3. Only once the resumed job runs clean, will the dependent health flag flip back and the recurring alert go silent. That flip-back is the completion verification.

### 3. Distinguish a real regression from a false positive

- If the underlying check is healthy and the alert is generated by a low-quality scorer (e.g. an LLM-as-judge flagging delivery-suppressed no-op turns ending in the literal `[SILENT]` token as quality regressions), the alert is a false positive — add the skip to the scorer, don't chase the alert.
- If a cron was genuinely removed/renamed, re-check `docs/fleet-reference.md` and the install script before assuming a silent gap is malicious.

## Pitfalls

- **Chasing the alert instead of the paused cron** wastes a session and leaves the root cause in place. The recurring, never-clearing pattern is the signal; trace it to the dead/inert job first.
- **Resuming on a still-present cause** re-trips the 3-failure pause within minutes. Verify the dependency first.
- **Trusting `last_status` of a paused job**: it stays `error` from the run that triggered the pause, so a paused job looks merely errored — check `paused_at`/`state` to see it is actually inert.
- **Verifying auto-resume by its report, not its side-effect.** A fixer run can resume a job (cooldown recorded, `state` flips to `scheduled`) yet print nothing because it returned early on an unrelated "no sensor output" branch before the report block. Before declaring the resume path broken or doubling up with a manual resume, check the cooldown/state file and the job's `state` — the side effect is the ground truth; the absence of a printed line is not.
